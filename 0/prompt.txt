I'd like to start a new project. My ultimate goal is to have a simple interface in gyrokinetic input files for requesting a Miller tokamak geometry, and provide only the minimum necessary inputs or functions that characterize that magnetic equilibrium. The gyrokinetic app would then generate an .eqdsk file, and run the rest of the simulation using the existing GKYL_GEOMETRY_TOKAMAK infrastructure.

To that end I'd like to proceed in 3 stages.

# Stage 1: clean up and extend existing python script for generating Miller eqdsk.

Gkeyll has a python script for generating Miller equilibrium,

gyrokinetic/data/eqdsk/write_efit_ltx_miller.py

It is presently tailored for the LTX tokamak. I'd like to create a new python script or module (name it gkeyll_gen_miller_eqdsk.py) based on this, but such that it works for any tokamak (size, magnetic field, safety factor, shear, etc). For example, I'd like to test it by generating eqdsk files for simulations like gyrokinetic/creg/rt_gk_d3d_iwl_3x2v_p1.c and gyrokinetic/creg/rt_gk_tcv_iwl_adapt_source_3x2v_p1.c also. I'd also like its geometry functions to be consistent with the latest version in, for example, gyrokinetic/creg/rt_gk_tcv_iwl_adapt_source_3x2v_p1.c.

# Stage 2: create a C version of gkeyll_gen_miller_eqdsk.py

In this stage translate gkeyll_gen_miller_eqdsk.py into an updater to be located in gyrokinetic/zero/ and implement unit tests for it, named gkyl_gen_miller_eqdsk.

# Stage 3: Plug gkyl_gen_miller_eqdsk into gyrokinetic app and provide new Miller API for input files.
In this stage we'll add a new enum gkyl_geometry_id option, say GKYL_GEOMETRY_MILLER, for which the user's input file will provide a minimum set of parameters and functions (in a sub struct member of gkyl_gk_geometry_inp like struct gkyl_miller_geo_grid_inp miller_grid_info). The gyrokinetic app will then call gkyl_gen_miller_eqdsk before initializing the geometry (around line 351 of gyrokinetic/apps/gyrokinetic.c), switch the geometry type to GKYL_GEOMETRY_TOKAMAK and perform the simulation as if this was a GKYL_GEOMETRY_TOKAMAK with a numerical magnetic equilibrium.

One detail is that for GKYL_GEOMETRY_TOKAMAK simulations the input file has input grid coordinate extents, specifically for the first dimension psi, which depend on knowledge of the eqdsk file (so that the user can pick the lower and upper psi). In this workflow it is perhaps not possible to pick psi a priori, so either: A) the user has to run the initialization once just to generate the eqdsk, examine it, pick psi bounds, and run the input file again, or B) the user provides the lower and upper normalized psi (i.e. rho = sqrt((psi - psi_axis)/(psi_sep - psi_axis)) assuming psi increasing outwards), and the app computes the psi bounds after the eqdsk is generated, or C) some other alternative I haven't thought of.
